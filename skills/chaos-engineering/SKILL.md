# Chaos Engineering — 系統韌性測試

> Wesley 的核心 QA 工具。用於在 Lab 進入孵化前驗證系統韌性，防止「在生產環境才發現的崩潰」。

> 「沒有終止條件的混沌實驗等於生產事故。」
>
> — Netflix Chaos Engineering Team

---

## Netflix 4 大混沌工程原則

1. **建立穩態假設** — 先定義「正常」是什麼，才能識別「異常」
2. **在生產環境驗證** — 測試環境通過不等於生產環境安全
3. **最小化爆炸半徑** — 從受控的小範圍開始，逐步擴大
4. **自動化持續執行** — 一次性測試無效，韌性需要持續驗證

## 三種進入模式

### Mode 1 — 設計新實驗

**Step 1：定義穩態（必要）**
```
系統：[名稱]
正常指標：
  - 成功率：≥ [X]%
  - 延遲 P99：≤ [X]ms
  - 錯誤率：≤ [X]%
測量方式：[監控工具/指標來源]
```

**Step 2：選擇攻擊類型**

| 攻擊類型 | 模擬場景 | 適用情境 |
|---|---|---|
| 延遲注入 | 服務回應變慢 50–5000ms | API 超時、慢查詢 |
| 錯誤注入 | 服務回傳 4XX / 5XX | 上游服務失敗 |
| 資源耗盡 | CPU/記憶體飆升 | 高負載場景 |
| 網路分割 | 服務間無法通訊 | 微服務依賴 |
| 依賴失敗 | 第三方 API 停止回應 | FinMind API、外部資料源 |
| 時間偏移 | 系統時間漂移 | 時間敏感計算 |
| 基礎設施故障 | 節點下線 | 分散式系統 |

**Step 3：設定終止條件（必填）**
- 成功率跌破 [X]% → 立即終止
- 錯誤率超過 [X]% → 立即終止
- 超過 [X] 分鐘 → 自動終止

**Step 4：計算爆炸半徑**

| 爆炸半徑 | 錯誤預算消耗 | 行動 |
|---|---|---|
| 🟢 GREEN | < 1% | 可安全執行 |
| 🟡 YELLOW | 1–10% | 需準備回滾，監控加強 |
| 🔴 RED | > 10% | 停止實驗，先修復系統 |

### Mode 2 — 執行中監控

持續監控以下信號：
- 實際錯誤率 vs 穩態基準
- 爆炸半徑是否擴散
- 是否觸發任何終止條件
- 用戶體驗是否受影響

**觸發緊急終止的條件（任一達到即停止）：**
- 錯誤率 > 設定上限
- 非目標服務開始異常
- 無法在 5 分鐘內手動恢復

### Mode 3 — 事後分析（Postmortem）

每次實驗結束後必須填寫：

```
## 混沌實驗事後分析

實驗名稱：[名稱]
執行日期：[日期]
持續時間：[X 分鐘]
攻擊類型：[類型]

### 結果
穩態是否維持：是 / 否
實際最大錯誤率：[X]%
用戶影響：有 / 無

### 發現的弱點
1. [問題描述] → 修復計畫：[...]
2. ...

### 系統韌性評分（0–100）
[評分] — [說明]

### 下次改善方向
[具體行動，含負責人與期限]
```

## Magic Lab 應用場景

| 場景 | 對應模式 |
|---|---|

| 任何生產事故後的根因分析 | Mode 3：事後分析 |

---

## 主動風險旗標（Wesley 主動提示）

- **無終止條件** — 設計實驗前若未定義終止條件，拒絕執行
- **跳過穩態定義** — 沒有基準就無從判斷影響，強制要求填寫
- **直接打生產** — 對 Magic Lab 而言，先在 `labs/` 沙盒驗證，再考慮 `projects/`
- **爆炸半徑未評估** — RED 爆炸半徑的實驗需要 Terry 批准才可執行
- **缺少事後分析** — 沒有學習的實驗是在浪費資源，每次實驗必須輸出 Postmortem
